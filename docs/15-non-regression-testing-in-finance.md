# Non-regression testing for a financial risk engine

Non-regression tests answer a practical release question:

> Did this change preserve previously approved behavior, calculations, contracts,
> and performance for the same inputs?

This is more specific than “the unit tests pass.” A refactor can preserve a
small method's unit tests while changing a query join, decimal rounding rule,
parallel aggregation order, or market-data interpretation.

## Why finance needs this discipline

A risk number is a function of more than source code:

```text
software release
+ position snapshot
+ market-data snapshot
+ model/methodology version
+ configuration and calendars
→ risk result
```

Therefore a regression fixture should identify its inputs and expected units,
currency, confidence, horizon, and methodology. Never build a regression test
from “today's market data”; the test would change every day.

## The implemented example

`tests/TradingRisk.Tests/Regression/RiskCalculationRegressionTests.cs` creates a
fixed portfolio and fixed historical-return scenarios, invokes the same
`CalculatePortfolioRiskHandler` used by the API, and asserts approved VaR,
Expected Shortfall, worst loss, volatility, and ordered scenario results. A
fixed `TimeProvider` keeps the calculation timestamp deterministic.

This is a small **golden calculation test**. The expected values are an explicit
approval baseline, not values generated by the implementation under test.

## Main non-regression layers

| Layer | Example failure caught |
| --- | --- |
| Golden calculation | VaR changes after a quantile or sign refactor |
| Market replay | a new curve/bootstrap or FX conversion changes a known date |
| Sensitivities | Delta/PV01 sign or unit changes |
| Stress scenarios | a rate shock stops producing the expected direction |
| API contract | JSON names, status codes, or Problem Details change |
| Persistence/query | a join duplicates positions or a filter loses a book |
| Determinism | multi-threaded and single-threaded results disagree |
| Performance | p99 latency, memory, or database round trips regress |

## Tolerances are part of the model

Exact decimal equality is appropriate when the algorithm deliberately uses
decimal values and has a stable rounding policy. Floating-point pricing may
need both an absolute and relative tolerance:

```text
abs(new - approved) <= 0.01
and
abs(new - approved) / max(abs(approved), 1) <= 0.0001
```

Do not widen a tolerance merely to make a failing test green. Investigate the
changed inputs, units, rounding, ordering, and methodology first. A material
change should produce a new model/version approval and an explanation.

## Release workflow

1. Run fast domain and application tests on every change.
2. Run golden fixtures against the fixed reference datasets.
3. Compare old/new outputs by portfolio, metric, currency, and scenario.
4. Classify differences: expected model change, bug fix, numerical noise, or
   unexplained regression.
5. Require model-owner/business approval for intentional result changes.
6. Run API, database, load, and deployment smoke tests before production.
7. Archive the release, fixture version, input snapshot, and comparison report.

## Good exercises

- Move the VaR quantile calculation and prove the fixture catches an off-by-one.
- Change scenario ordering and prove the report remains deterministic.
- Introduce a duplicated EF join and add a query regression fixture.
- Run the calculator with two worker partitions and compare the result with the
  single-worker baseline.
- Add a performance gate for 10,000 scenarios and document the machine/profile.

Non-regression testing is not a substitute for model validation or independent
risk review. It is the repeatable software-release safety net around them.
